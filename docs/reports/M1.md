## 1. Summary

Milestone M1 establishes the structural core of the S-ERP DBMS application by delivering identical relational data models across two production-grade RDBMS engines: **MySQL 8.4** and **PostgreSQL 16**. 

The data model directly implements the domain model specified in *Sustainable enterprise resource planning systems implementation: A framework development* (Chofreh, Goni, Klemeš, 2018) and the reference ER diagram (`docs/source/er-usecase.png`). It captures 21 total tables (17 business entities and 4 bridging/gap associations) with full normalization, primary and foreign key constraints, `ON DELETE` rules, and database-level `CHECK` constraints. 

All tables are populated with realistic demonstration data through an idempotent seeding pipeline (`scripts/seed.ts`), producing exactly identical row counts (133 rows across 21 tables) and foreign key relationships (29 FK constraints) across both engines. Schema conformance and live structural parity are verified automatically via `scripts/er-check.ts` and automated test suites (`tests/schema.test.ts`).

## 4. Database Detail

### 4.1 Schema Additions & Structure

The schema defines **21 tables** grouped by business domain:

1. **Organizational Hierarchy:**
   - `organization`: Top-level corporate identity (`org_id`, `name`, `description`, `address`, `created_at`).
   - `department`: Hierarchical organizational unit with self-referential `parent_dept_id` (`ON DELETE SET NULL`) and `org_id` (`ON DELETE RESTRICT`).
   - `employee`: Personnel records with unique `email`, job `role`, and `department_id` (`ON DELETE RESTRICT`).
   - `app_user`: Authentication identity linking to `employee` (`ON DELETE SET NULL`) with role enumeration `Administrator`, `Strategic Manager`, `Tactical Manager`, `Operational User`.

2. **Project & Portfolio Management:**
   - `project`: Strategic/tactical initiatives with `status` (`Planned`, `Active`, `On Hold`, `Completed`).
   - `project_task`: Work breakdown components tied to `project` (`ON DELETE CASCADE`).
   - `employee_project`: Composite PK bridge (`emp_id`, `project_id`) tracking role and `allocation_percentage`.
   - `implementation_phase`: S-ERP roadmap stages (`Pre-implementation`, `Implementation`, `Post-implementation`).
   - `risk`: Project risks with level constraint (`Low`, `Medium`, `High`).

3. **Sustainability Core (Chofreh et al. / Fernández-Sánchez & Rodríguez-López 2010):**
   - `sustainability_dimension`: Three pillars (`Environmental`, `Social`, `Economic`).
   - `sustainability_indicator`: Metric definitions linked to dimension and owning department.
   - `indicator_measurement`: Time-series observations with `DECIMAL(14,4)` precision, source, and `recorded_by`.

4. **Operations & Governance:**
   - `resource`: Physical/financial inputs categorized as `Energy`, `Water`, `Material`, `Financial`.
   - `business_process`: Operational flows mapped to departments.
   - `process_resource`: Quantitative allocation of resources to processes.
   - `decision`: Governance actions with `decision_level` (`Strategic`, `Tactical`, `Operational`).
   - `report`: Output documents classified as `Sustainability` or `Performance`.

5. **Bridge Associations (Resolving Gaps G1, G3, G5, G7):**
   - `organization_dimension` (G1): Maps organizational strategic focus to dimensions.
   - `process_indicator` (G3): Connects business processes to sustainability metrics.
   - `decision_risk` (G5): Associates risks directly to mitigating decisions.
   - `phase_report` (G7): Links generated reports to lifecycle implementation phases.

### 4.2 Engine Differences Observed

| Feature / Behavior | MySQL 8.4 | PostgreSQL 16 |
|---|---|---|
| Primary Key Generation | `INT AUTO_INCREMENT PRIMARY KEY` | `INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` |
| Timestamps | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| Boolean Storage | `TINYINT(1) DEFAULT 1` | Native `BOOLEAN DEFAULT TRUE` |
| Parameter Placeholders | Positional question marks `?` | Positional indexed numbers `$1, $2, ...` |
| Insert ID Retrieval | `result.insertId` returned via protocol packet | `RETURNING col` clause in SQL |
| Foreign Key Checks Toggle | `SET FOREIGN_KEY_CHECKS = 0 / 1;` | `DROP TABLE ... CASCADE` / `TRUNCATE ... CASCADE` |
| Identifiers & Case | Case-insensitive table matching on Linux by default config | Strict case-sensitivity; all lower_case snake_case without quotes |

## 5. How It Works

1. **Container Startup:** `docker-compose.yml` launches MySQL 8.4 on port 3307 and PostgreSQL 16 on port 5434. Both containers run with memory caps of 512 MB.
2. **Schema Migration:** Running `npm run migrate` reads `db/mysql/schema.sql` and executes it via `mysql2`, then reads `db/postgres/schema.sql` and executes it via `pg`.
3. **Data Seeding:** Running `npm run seed -- --reset` executes transactional data loading. It seeds organizational foundations, indicator taxonomies, demo projects, tasks, resources, and 12-month measurements.
4. **Live Verification:** `npm run er-check` queries `information_schema` on both live servers, verifies that all 21 tables exist, compares row counts, counts FK constraints, and logs a clean verification table.
5. **Acceptance Testing:** `npm run test` executes `tests/schema.test.ts`, asserting row count parity and proving that CHECK constraints and FK constraints block invalid operations on both database engines.

## 8. Deviations & Decisions

The following architectural decisions implement the gap resolutions defined in `plan.md` §4:

1. **G1 (Organization ↔ Dimension):** Created bridge table `organization_dimension(org_id, dimension_id)` with composite PK and foreign keys referencing `organization` and `sustainability_dimension`.
2. **G2 (Department ↔ Indicator):** Added nullable `department_id` foreign key on `sustainability_indicator` referencing `department(dept_id)` (`ON DELETE SET NULL`).
3. **G3 (Process ↔ Indicator):** Created bridge table `process_indicator(process_id, indicator_id)` with composite PK and cascade deletion.
4. **G4 (Decision ↔ Process):** Added nullable `process_id` foreign key on `decision` referencing `business_process(process_id)` (`ON DELETE SET NULL`).
5. **G5 (Decision ↔ Risk):** Created bridge table `decision_risk(decision_id, risk_id)` with composite PK and cascade deletion.
6. **G6 (Risk ↔ Phase):** Linked through mutual association to `project_id`.
7. **G7 (Phase ↔ Report):** Created bridge table `phase_report(phase_id, report_id)` with composite PK and cascade deletion.
8. **G8 (App User / Roles):** Created `app_user` with hashed passwords (`bcryptjs`), role check constraint (`Administrator`, `Strategic Manager`, `Tactical Manager`, `Operational User`), and optional link to `employee`.
9. **G9 (Measurement Audit):** Added nullable `recorded_by` foreign key referencing `app_user(user_id)` on `indicator_measurement` (`ON DELETE SET NULL`).

## 9. Known Issues and Limitations

1. **Single-Node Standalone Execution:** Dual databases run in independent single-node Docker containers without replication or cross-engine data synchronization, in strict conformance with the DBMS design requirement that both engines hold independent demo datasets.
2. **Docker Port Mappings:** MySQL runs mapped to host port `3307` (to prevent collision with default host MySQL installations), and PostgreSQL runs mapped to host port `5434` (to avoid collision with default host PostgreSQL port 5432).
