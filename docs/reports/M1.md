## 1. Summary

Milestone M1 establishes the dual-engine foundation of the S-ERP DBMS application by delivering identical relational-to-document entity models across two interchangeable database paradigms: **Relational SQL (MySQL 8.4)** and **Document NoSQL (MongoDB 6.0)**. PostgreSQL was removed from the project per directive and replaced with native MongoDB 6.0 support.

The data model directly implements the domain model specified in *Sustainable enterprise resource planning systems implementation: A framework development* (Chofreh, Goni, Klemeš, 2018) and the reference ER diagram (`docs/source/er-usecase.png`). It captures 21 total entities (17 business entities and 4 bridging/gap associations) with full relational integrity in MySQL and matching collection indexing in MongoDB.

All entities are populated with realistic demonstration data through an idempotent seeding pipeline (`scripts/seed.ts`), producing exactly identical entity and document counts (133 records across 21 entities) on both MySQL 8.4 and MongoDB 6.0. Schema conformance and live structural parity are verified automatically via `scripts/er-check.ts` and automated test suites (`tests/schema.test.ts`).

## 4. Database Detail

### 4.1 Schema Additions & Structure

The schema defines **21 entities** grouped by business domain:

1. **Organizational Hierarchy:**
   - `organization`: Top-level corporate identity (`org_id`, `name`, `description`, `address`, `created_at`).
   - `department`: Hierarchical organizational unit with self-referential `parent_dept_id` (`ON DELETE SET NULL`) and `org_id` (`ON DELETE RESTRICT`).
   - `employee`: Personnel records with unique `email`, job `role`, and `department_id` (`ON DELETE RESTRICT`).
   - `app_user`: Authentication identity linking to `employee` (`ON DELETE SET NULL`) with role enumeration `Administrator`, `Strategic Manager`, `Tactical Manager`, `Operational User`.

2. **Project & Portfolio Management:**
   - `project`: Strategic/tactical initiatives with `status` (`Planned`, `Active`, `On Hold`, `Completed`).
   - `project_task`: Work breakdown components tied to `project` (`ON DELETE CASCADE`).
   - `employee_project`: Composite PK bridge (`emp_id`, `project_id`) tracking role and `allocation_percentage`.
   - `implementation_phase`: S-ERP roadmap stages (`Pre-implementation`, `Implementation`, `Post-implementation`).
   - `risk`: Project risks with level constraint (`Low`, `Medium`, `High`).

3. **Sustainability Core (Chofreh et al. / Fernández-Sánchez & Rodríguez-López 2010):**
   - `sustainability_dimension`: Three pillars (`Environmental`, `Social`, `Economic`).
   - `sustainability_indicator`: Metric definitions linked to dimension and owning department.
   - `indicator_measurement`: Time-series observations with `DECIMAL(14,4)` precision, source, and `recorded_by`.

4. **Operations & Governance:**
   - `resource`: Physical/financial inputs categorized as `Energy`, `Water`, `Material`, `Financial`.
   - `business_process`: Operational flows mapped to departments.
   - `process_resource`: Quantitative allocation of resources to processes.
   - `decision`: Governance actions with `decision_level` (`Strategic`, `Tactical`, `Operational`).
   - `report`: Output documents classified as `Sustainability` or `Performance`.

5. **Bridge Associations (Resolving Gaps G1, G3, G5, G7):**
   - `organization_dimension` (G1): Maps organizational strategic focus to dimensions.
   - `process_indicator` (G3): Connects business processes to sustainability metrics.
   - `decision_risk` (G5): Associates risks directly to mitigating decisions.
   - `phase_report` (G7): Links generated reports to lifecycle implementation phases.

### 4.2 Engine Differences Observed

| Feature / Behavior | Relational SQL (MySQL 8.4) | Document NoSQL (MongoDB 6.0) |
|---|---|---|
| Storage Unit | Normalized tables with typed columns | Flexible BSON document collections |
| Primary Key | `INT AUTO_INCREMENT PRIMARY KEY` | Integer ID maintained + native BSON `_id` |
| Constraint Enforcement | Database DDL (`FOREIGN KEY`, `CHECK`) | Unique indexes + Application Adapter validation |
| Parameter Placeholders | Positional question marks `?` | Parameter array mapped via AlaSQL parser |
| Query Translation | Native SQL execution via `mysql2` | SQL parsed and executed against collections via AlaSQL / Mongo query API |
| Transactions | Native ACID transactions (`BEGIN`/`COMMIT`) | Client transactions (`withSession`) |

## 5. How It Works

1. **Container Startup:** `docker-compose.yml` launches MySQL 8.4 on port 3307 and MongoDB 6.0 on port 27017. Both containers run with memory caps of 512 MB.
2. **Schema Migration:** Running `npm run migrate` reads `db/mysql/schema.sql` and executes DDL via `mysql2`, then initializes 21 collections and unique/referential indexes in MongoDB via `mongodb`.
3. **Data Seeding:** Running `npm run seed -- --reset` executes transactional data loading. It seeds organizational foundations, indicator taxonomies, demo projects, tasks, resources, and 12-month measurements into both engines.
4. **Live Verification:** `npm run er-check` queries `information_schema` on MySQL and collection counts on MongoDB, verifies that all 21 entities exist, compares row/doc counts, and logs a clean verification table.
5. **Acceptance Testing:** `npm run test` executes `tests/schema.test.ts`, asserting exact row/doc count parity (133 records across 21 entities) and proving that constraints and indexes block invalid operations on both database engines.

## 8. Deviations & Decisions

1. **Engine Pivot to MongoDB:** In accordance with the owner's directive, PostgreSQL was removed and replaced with MongoDB 6.0, establishing a SQL vs NoSQL dual-engine paradigm.
2. **AlaSQL / Mongo Adapter Architecture:** SQL queries from route handlers run natively on MySQL and are parsed by AlaSQL into in-memory document operations against MongoDB collections, ensuring identical query capabilities without requiring separate repositories.
3. **G1 (Organization ↔ Dimension):** Created bridge entity `organization_dimension(org_id, dimension_id)`.
4. **G2 (Department ↔ Indicator):** Added nullable `department_id` on `sustainability_indicator`.
5. **G3 (Process ↔ Indicator):** Created bridge entity `process_indicator(process_id, indicator_id)`.
6. **G4 (Decision ↔ Process):** Added nullable `process_id` on `decision`.
7. **G5 (Decision ↔ Risk):** Created bridge entity `decision_risk(decision_id, risk_id)`.
8. **G6 (Risk ↔ Phase):** Linked through mutual association to `project_id`.
9. **G7 (Phase ↔ Report):** Created bridge entity `phase_report(phase_id, report_id)`.
10. **G8 (App User / Roles):** Created `app_user` with hashed passwords (`bcryptjs`) and 4 enumerated roles.
11. **G9 (Measurement Audit):** Added nullable `recorded_by` on `indicator_measurement`.

## 9. Known Issues and Limitations

1. **Dual Independent Datasets:** MySQL and MongoDB operate completely independently without cross-database synchronization, in accordance with the project's specification.
2. **MongoDB Port:** MongoDB runs on default port `27017` and MySQL on port `3307`.
