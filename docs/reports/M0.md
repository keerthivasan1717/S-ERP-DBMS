## 1. Summary

Milestone M0 establishes the engineering baseline, repository structure, dual-database runtime infrastructure, code verification pipeline, and automated reporting system for the Sustainable Enterprise Resource Planning (S-ERP) DBMS project.

The system is architected around Node.js 20 LTS, TypeScript (strict mode), Express 4, and direct database connectivity using native drivers (`mysql2` and `pg`) with **no ORM**. Both MySQL 8.4 and PostgreSQL 16 containers have been configured via `docker-compose.yml`, strictly enforcing a `512MB` RAM ceiling per container to adhere to host constraints. A live diagnostic endpoint (`GET /api/engines/status`) was implemented to actively verify host reachability, connection latency, and exact database engine versions on demand. Furthermore, the report toolchain was authored to compile this and future milestone reports into A4 PDF documents styled in conformance with the project's ledger-themed aesthetic palette and typographic rules, complete with git commit metadata and page numbering.

### Research Paper to Product Mapping Table (from `plan.md` §1)

The conceptual foundations of this DBMS implementation originate from *Sustainable enterprise resource planning systems implementation: A framework development* (Chofreh et al., 2018). The table below outlines how core principles from the paper translate directly into concrete architectural elements of this system:

| Paper Principle / Requirement | Implementation in S-ERP DBMS |
|---|---|
| **Sustainability Paradigm** (Environmental, Social, Economic) | Dedicated `sustainability_dimension` table; each indicator is classified into one of the three dimensions; dashboards and reports aggregate metrics by dimension. |
| **Sustainability Indicators** (Paper Fig. 5, Fernández-Sánchez & Rodríguez-López 2010) | Master seed catalog for `sustainability_indicator` covering 9 Environmental, 7 Social, and 5 Economic indicators. |
| **Decisional Paradigm** (Strategic, Tactical, Operational) | Categorized in `decision.decision_level`; four distinct user roles with dedicated interfaces and server-enforced access controls. |
| **Project Management** (5 process groups, 10 knowledge areas) | Structured management across `project`, `project_task`, `implementation_phase`, and `risk` tables. |
| **S-ERP Roadmap** (Pre-implementation, Implementation, Post-implementation) | Seeded phases representing ERP deployment lifecycle milestones in `implementation_phase`. |
| **Integrated Database** (Elimination of functional data silos) | Unified, 3NF relational schema shared across all modules with zero duplicate master entities. |
| **Automated Sustainability Reporting** (Eliminating manual spreadsheets) | First-class `report` entity with automatic calculation, archiving, and parameter-driven PDF export. |
| **Triple Bottom Line Alignment** | Decisions link processes, resources, and projects; dashboards render all three dimensions side by side. |

  - Image: `mysql:8.4`
  - Container Name: `serp_mysql`
  - Memory Limit: `512MB`
  - Host Port: `3307` (Container Port `3306`)
  - Volume: `serp_mysql_data`
  - Healthcheck: `mysqladmin ping -h 127.0.0.1 -u root -p$MYSQL_ROOT_PASSWORD`
- **PostgreSQL 16:**
  - Image: `postgres:16-alpine`
  - Container Name: `serp_postgres`
  - Memory Limit: `512MB`
  - Host Port: `5434` (Container Port `5432`)
  - Volume: `serp_postgres_data`
  - Healthcheck: `pg_isready -U $POSTGRES_USER -d $POSTGRES_DB`

### 4.2 Engine Differences Observed in M0
| Dimension | MySQL 8.4 | PostgreSQL 16 |
|---|---|---|
| **Driver Package** | `mysql2/promise` | `pg` (`Client`) |
| **Version Probe Query** | `SELECT VERSION() as version` | `SELECT version()` |
| **Response Format** | Array of plain row objects `[ { version: '8.4.13' } ]` | QueryResult object with `.rows[0].version` containing full architecture/compiler banner |
| **Default Port** | `3306` (host mapped to `3307`) | `5432` (host mapped to `5434`) |

## 5. How It Works

1. **Environment Initialization:**
   The backend loads and validates environment variables from `.env` using Zod (`server/src/config/env.ts`). If any configuration is malformed, the process immediately halts with descriptive schema errors.
2. **Container Health Monitoring:**
   Docker Compose initiates MySQL 8.4 and PostgreSQL 16 with memory constraints (`512MB`). Internal healthchecks periodically test database readiness.
3. **Dual Engine Probe:**
   When a client requests `GET /api/engines/status`:
   - An asynchronous probe connects to MySQL at `127.0.0.1:3307` and executes `SELECT VERSION()`.
   - Concurrently, an asynchronous probe connects to PostgreSQL at `127.0.0.1:5434` and executes `SELECT version()`.
   - Both connections use strict timeouts (3000ms) and automatically close their sockets upon completion.
   - The aggregated status is returned with HTTP 200 (if both engines are active) or HTTP 503 (if either engine fails).
4. **Report Pipeline:**
   Executing `npm run report -- M0` reads `docs/reports/M0.md`, embeds current git revision and date, renders Markdown to HTML via `marked`, injects `docs/reports/report.css`, and renders `docs/reports/M0-foundations.pdf` via Puppeteer with headers and footers.

## 8. Deviations & Decisions

1. **Host Port Offsets (`3307` and `5434`):**
   - *Rationale:* The developer host environment had existing system services occupying default ports (`3306` for MariaDB and `5432` for PostgreSQL). Docker Compose was configured to map container port `3306` to host `3307`, and container port `5432` to host `5434`. This avoids host port collisions while ensuring the Dockerized environments match `MySQL 8.4` and `PostgreSQL 16` specifications exactly.
2. **Filesystem Execution Isolation (NTFS mount compatibility):**
   - *Rationale:* The workspace repository resides on a fuseblk/NTFS mounted volume with `noexec` permission defaults. Direct execution of native node binaries (such as `esbuild`) from inside `node_modules` is blocked by the OS kernel (`EACCES`). To ensure 100% build reliability without altering drive mount flags, all npm scripts execute via explicit node invocations (`node ./node_modules/...`) and `tsc` pre-compilation, while `esbuild` fallback paths are directed to user-space cache.
3. **Puppeteer Standalone Headless Engine:**
   - *Rationale:* To avoid dependency on system-level Chrome packages that may not be installed on clean machines, Puppeteer is configured with `chrome-headless-shell` residing in the user cache directory (`~/.cache/puppeteer`).

## 9. Known Issues and Limitations

- **Container Startup Period:** MySQL 8.4 requires approximately 15–20 seconds to complete internal data directory initialization before its healthcheck transitions to `healthy`. The backend probe gracefully handles this transient phase by returning `reachable: false` and HTTP 503 until the engine is fully online.
- **Single Host Deployment:** Both engines run on the local Docker network; distributed network replication between engines is intentionally omitted per `GEMINI.md` §5 (separate, independent data).

```bash
# 1. Copy environment template
cp .env.example .env

docker compose up -d

npm run build:server
npm run dev:server &
```
