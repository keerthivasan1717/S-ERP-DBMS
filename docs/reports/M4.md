## 1. Summary

Milestone M4 establishes the full organizational structure and administrative governance suite for the S-ERP DBMS application. Designed exclusively for the `Administrator` role, this milestone delivers complete lifecycle management across the four primary organizational entities: Organization Profile (`organization`), Department Hierarchy (`department`), Personnel Directory (`employee`), and User Accounts (`app_user`).

Key deliverables accomplished in this milestone:
1. **Interactive Department Hierarchy Tree & Ledger (`DepartmentsPage.tsx`):** Implemented a dual-view department module displaying both an interactive nested hierarchy tree (illustrating parent-child relationships and assigned employee tallies) and a high-density ledger table.
2. **Referential Integrity & Delete Conflict Protection:** Rigorously enforced relational integrity constraints across both SQL and NoSQL engines. Deletion of departments possessing active assigned employees or child subdepartments is blocked on both server and client layers with an explicit HTTP 409 Conflict error (`"Department has assigned employees. Reassign them before deleting."`).
3. **Personnel & User Lifecycle Management (`EmployeesPage.tsx`, `UsersPage.tsx`):** Full CRUD capability for employees with unique email constraints, role designations, and department mappings. User account lifecycle management with bcrypt password reset (cost factor 12), user-to-employee relational linkage, role assignment, and immediate account deactivation/activation toggles.
4. **Strategic Sustainability Focus Links (Gap G1):** Direct bridge association (`organization_dimension`) connecting the top-level organization with sustainability dimensions (`Environmental`, `Social`, `Economic`), allowing administrators to manage organizational policy focus areas.
5. **Dual-Engine Automated Testing:** 57 test cases across 5 test suites verifying complete CRUD workflows, integrity rejections, and state transitions across both MySQL 8.4 and MongoDB 6.0.

## 4. Database Detail

### 4.1 Referential Integrity Enforcement

To ensure identical behavior across MySQL (SQL) and MongoDB (NoSQL), referential integrity is guaranteed at both database engine and adapter repository layers:

```typescript
// Conflict guard in AdminRepo.deleteDepartment
const empCount = await this.db.one<any>(
  'SELECT COUNT(*) AS c FROM employee WHERE department_id = ?',
  [deptId]
);
if (Number(empCount?.c || 0) > 0) {
  throw new Error('CONFLICT: Department has assigned employees. Reassign them before deleting.');
}

const childCount = await this.db.one<any>(
  'SELECT COUNT(*) AS c FROM department WHERE parent_dept_id = ?',
  [deptId]
);
if (Number(childCount?.c || 0) > 0) {
  throw new Error('CONFLICT: Department has sub-departments. Reassign or remove them first.');
}
```

### 4.2 Engine Differences Handled

| Feature / Behavior | MySQL 8.4 | MongoDB 6.0 | Adapter Resolution |
|---|---|---|---|
| **Department Foreign Keys** | `FOREIGN KEY (parent_dept_id) REFERENCES department(dept_id) ON DELETE SET NULL` | BSON collection reference `parent_dept_id` integer | `AdminRepo` explicitly queries child counts before deletion; MySQL rejects via engine FK while MongoDB is guarded via repository check. |
| **Employee Foreign Keys** | `FOREIGN KEY (department_id) REFERENCES department(dept_id) ON DELETE RESTRICT` | Document field `department_id` indexed | Both engines return HTTP 409 with identical error payload when deletion is attempted on an occupied department. |
| **User Deactivation Effect** | `is_active TINYINT(1) DEFAULT 1` | BSON boolean `is_active: true` | `POST /api/auth/login` checks `!user.is_active` and immediately rejects login with HTTP 403 Forbidden. |
| **Organization Dimension (G1)** | Composite PK `(org_id, dimension_id)` | Unique compound index `{ org_id: 1, dimension_id: 1 }` | `AdminRepo.updateOrganization` synchronizes links within atomic update blocks. |

## 5. How It Works

### 5.1 Department Hierarchy Management & Deletion Guard
1. **Hierarchy Rendering:** `DepartmentsPage.tsx` fetches departments via `GET /api/admin/departments`. An in-memory tree grouping partitions nodes by `parent_dept_id`, rendering top-level departments and recursive indented child units with employee count badges.
2. **Creation / Edit:** Administrator submits department name, optional parent department selector, and description. The backend inserts or updates `department` with `parent_dept_id`.
3. **Deletion Attempt on Occupied Department:** Administrator clicks "Delete" on department #1 (Engineering). `DELETE /api/admin/departments/1` executes.
4. **Conflict Halting:** `AdminRepo` detects that department #1 has 8 assigned employees and throws a `CONFLICT` error. Express intercepts and returns `HTTP 409 Conflict` with JSON message: `"Department has assigned employees. Reassign them before deleting."`

### 5.2 User Account Lifecycle & Deactivation
1. **Creation & Linking:** Administrator navigates to User Accounts and clicks "+ Create User". Enters username, password (`InitialPassword123`), role (`Operational User`), and selects an employee link.
2. **Bcrypt Hashing:** `POST /api/admin/users` validates payload via Zod, generates a bcrypt hash with cost factor 12, and inserts the user record.
3. **Password Reset & Deactivation:** Administrator edits user, enters a new password, and toggles Active to `false`. `PUT /api/admin/users/:id` re-hashes the password and sets `is_active = false`.
4. **Login Enforcement:** If the deactivated user attempts to sign in via `POST /api/auth/login`, the server rejects authentication with `HTTP 403 Forbidden: "This user account is deactivated."`

## 8. Deviations & Decisions

| Decision / Deviation | Rationale |
|---|---|
| **Dual View for Departments (Tree + Ledger)** | While `plan.md` required a department tree view, dense tabular controls are also essential for high-volume editing. Both were integrated into `DepartmentsPage.tsx` using a unified hierarchy renderer. |
| **Two-Tier Deletion Guard** | Enforced department deletion conflict checks in `AdminRepo` for both employees and child subdepartments before issuing SQL DELETE, ensuring MongoDB produces identical HTTP 409 responses to MySQL. |
| **Immediate Login Ban for Deactivated Users** | Verified in `POST /api/auth/login` that deactivated users cannot sign in regardless of valid credentials, returning HTTP 403. |

---

## 9. Known Issues and Limitations

1. **Cycle Prevention in Department Hierarchy:** Department parent assignments currently prevent a department from selecting itself as parent; multi-tier circular dependency checks (e.g. A -> B -> A) should be validated in future migrations.
2. **Cascading Department Deletions:** Deleting a department requires manual reassignment of all associated employees and sub-departments first, by intentional design to safeguard personnel data.
