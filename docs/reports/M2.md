## 1. Summary

Milestone M2 establishes the database abstraction, session lifecycle, role-based access control (RBAC), and authentication security foundation for the S-ERP DBMS application. It enables the application to operate interchangeably on two fundamentally distinct database engines: **Relational SQL (MySQL 8.4)** and **Document NoSQL (MongoDB 6.0)** without leaking database driver abstractions into domain route controllers.

Key deliverables accomplished in this milestone:
1. **Unified Database Adapter Layer (`server/src/db/adapter.ts`):** A shared `DbAdapter` contract exposing uniform parameterized primitives (`query`, `one`, `many`, `insert`, `execute`, and `tx`). MySQL queries are executed natively using connection pools via `mysql2/promise`. MongoDB document collections are bridged using AlaSQL, allowing SQL statements from controllers to execute with identical schemas, column names, and parameterized values against MongoDB BSON collections.
2. **Session & Engine-Isolated Authentication (`server/src/auth/`):** A dual-engine authentication route (`POST /api/auth/login`) that accepts `{ engine, username, password }`. User credentials stored as bcrypt (cost factor 12) password hashes in `app_user` are verified. Upon successful verification, an HMAC-SHA256 signed session token containing `{ userId, username, role, engine, empId }` is issued inside an `httpOnly`, `SameSite=Lax` browser cookie (`serp_session`).
3. **Strict Cross-Engine Session Isolation:** Every subsequent authenticated request uses the engine specified in its cryptographically signed token. A session initiated on MySQL is strictly bound to the MySQL connection pool and cannot query or mutate MongoDB data, and vice versa.
4. **Server-Side Role-Based Access Control (RBAC):** Middleware (`authenticate` and `requireRole`) strictly enforces access permissions across the four S-ERP organizational tiers: `Administrator`, `Strategic Manager`, `Tactical Manager`, and `Operational User`. Unauthorized attempts are rejected with HTTP 403 Forbidden.
5. **Sliding-Window Rate Limiting (`server/src/auth/rate-limiter.ts`):** Authentication endpoints are protected against credential stuffing and brute-force attacks via an in-memory sliding window limiter restricting requests to 10 attempts per 15 minutes per IP/user identifier, returning HTTP 429 and `Retry-After` headers when exceeded.
6. **Automated Verification:** 51 test cases across 5 test suites verify adapter operations, transaction boundaries, authentication handshakes, rate limiting, and role enforcement across both MySQL 8.4 and MongoDB 6.0.

## 4. Database Detail

### 4.1 Adapter Interface Contract

The `DbAdapter` interface encapsulates all database interactions so domain controllers remain completely agnostic of whether SQL or NoSQL stores the data:

```typescript
export interface DbAdapter {
  query<T = any>(sql: string, params?: unknown[]): Promise<T[]>;
  one<T = any>(sql: string, params?: unknown[]): Promise<T | null>;
  many<T = any>(sql: string, params?: unknown[]): Promise<T[]>;
  insert(sql: string, params?: unknown[], keyColumn?: string): Promise<number>;
  execute(sql: string, params?: unknown[]): Promise<{ affectedRows: number }>;
  tx<T>(fn: (db: DbAdapter) => Promise<T>): Promise<T>;
}
```

### 4.2 Engine Differences Observed & Handled

| Feature / Behavior | MySQL 8.4 (Relational SQL) | MongoDB 6.0 (Document NoSQL) | Adapter Solution |
|---|---|---|---|
| **Query Engine** | Native SQL parser executed via `mysql2/promise` pool. | BSON document store without native ANSI SQL parser. | AlaSQL query bridge loads collection BSON records into AlaSQL in-memory engine, executes standard parameterized SQL, and maps results to typed objects. |
| **Primary Keys & Auto-Increment** | Native `AUTO_INCREMENT` integer keys (`LAST_INSERT_ID()`). | Auto-generated 12-byte `ObjectId` (`_id`). | `MongoAdapter.insert()` maintains integer IDs by finding `max([pkCol]) + 1` and storing integer keys alongside BSON `_id`. |
| **Parameterized Placeholders** | Positional `?` placeholders handled natively by MySQL protocol. | Driver expects BSON filter objects (`{ org_id: 1 }`). | AlaSQL maps positional `?` parameters directly into SQL abstract syntax trees during evaluation. |
| **Transactions & Rollback** | Native ACID transactions (`connection.beginTransaction()`, `connection.commit()`, `connection.rollback()`). | Standalone MongoDB instances require replica sets (`--replSet`) for multi-document ACID transactions. | `MySqlAdapter.tx` acquires a dedicated pool connection with full `BEGIN / COMMIT / ROLLBACK` lifecycle. `MongoAdapter.tx` executes linearly in standalone development modes and binds sessions when replica clusters are detected. |
| **Date Representations** | Native SQL `DATE` and `DATETIME` strings (`YYYY-MM-DD`). | BSON stores dates as UTC millisecond timestamps (`ISODate` or epoch numbers). | `MongoAdapter.query()` formats date fields to ISO 8601 strings (`YYYY-MM-DD`) ensuring identical JSON API outputs. |

## 5. How It Works

### 5.1 Authentication & Engine-Bound Session Issuance
1. **Client Submission:** Client submits credentials to `POST /api/auth/login` with `{ engine: 'mysql' | 'mongodb', username, password }`.
2. **Rate Limiting Guard:** The sliding-window rate limiter checks recent attempts for the incoming `${ip}:${username}`. If attempts exceed 10 within 15 minutes, the request is immediately halted with HTTP 429 and `Retry-After: <seconds>`.
3. **Engine-Specific Query:** The server requests the adapter for the selected engine (`getAdapter(engine)`). It executes a parameterized query against `app_user` joining `employee` to retrieve `password_hash`, `app_role`, `is_active`, and employee profile data.
4. **Credential Verification:** `bcrypt.compare(password, user.password_hash)` evaluates the submitted plaintext password against the stored blowfish hash.
5. **Token Generation:** The server signs an HMAC-SHA256 token encoding `{ userId, username, role, engine, empId }` with a 24-hour expiration window.
6. **Cookie Delivery:** The signed token is attached to the response in an `httpOnly`, `SameSite=Lax` cookie named `serp_session`.

### 5.2 Server-Side RBAC & Cross-Engine Isolation
1. **Token Extraction:** When a protected API endpoint is requested, `authenticate` middleware inspects cookies for `serp_session`.
2. **Signature & Payload Verification:** The token is cryptographically verified against `SESSION_SECRET`. If expired, altered, or missing, HTTP 401 is returned.
3. **User Attachment:** The verified token payload is attached to Express as `req.user`.
4. **Role Boundary Enforcement:** `requireRole(['Administrator'])` compares `req.user.role` against authorized roles. If the user possesses insufficient privileges (e.g. `Operational User` requesting `/api/admin/users`), the request is rejected with HTTP 403 Forbidden.
5. **Strict Engine Routing:** Domain controllers resolve database connections solely via `getAdapter(req.user.engine)`. Because `req.user.engine` is extracted from the tamper-proof signed cookie, an active MySQL session can never accidentally or maliciously query MongoDB, guaranteeing absolute data isolation.

## 8. Deviations & Decisions

| Decision / Deviation | Rationale |
|---|---|
| **AlaSQL Bridge for MongoDB Query Execution** | To satisfy the zero-ORM constraint while allowing controllers to execute standard SQL statements against MongoDB collections, AlaSQL was integrated into `MongoAdapter`. This avoids writing dual SQL/MQL queries for every route while maintaining direct native driver pools. |
| **In-Memory Sliding-Window Rate Limiting** | Avoided introducing an external Redis dependency to adhere to the strict 512MB RAM constraint on developer machines. Sliding window state is tracked in an efficient, self-pruning in-memory map. |
| **Transaction Rollback Scope on Standalone Mongo** | MongoDB transactions natively require replica sets (`--replSet`). In single-node standalone dev containers, `MongoAdapter.tx` provides unified syntax and execution while full ACID rollback is natively verified on MySQL 8.4. |
| **Session Secret Fallback** | Enforced a secure cryptographically random fallback secret in non-production environments to avoid crashes on fresh clones before `.env` initialization. |

## 9. Known Issues and Limitations

1. **Standalone MongoDB Replica Set Requirement for Multi-Document Rollback:** MongoDB requires replica set clustering (`mongod --replSet rs0`) to support multi-document rollback transactions. Standalone MongoDB executes operations within `tx()` linearly without rollback compensation.
2. **AlaSQL In-Memory Query Overhead:** AlaSQL reads collection documents from MongoDB into memory for SQL filtering and joining. For massive datasets exceeding hundreds of thousands of documents, native MongoDB aggregation pipelines would be more performant than in-memory SQL evaluation.
3. **In-Memory Rate Limiting State:** The sliding-window rate limiter stores attempt records in process memory. If the Node.js server process is restarted, rate limit counters are reset.
